# Модули проекта (независимая разработка)

Проект растёт — фиксируем **границы модулей**, чтобы их можно было пилить
параллельно, тестировать изолированно и не плодить связность. Это **не** переписка
кода: мы проводим линии по уже существующей структуре (слои из CLAUDE.md + уже
готовые `core/ports` + `DIContainer`) и добавляем правило зависимостей и его
проверку.

## Принцип: модуль = папка + публичный порт + правило зависимостей

1. **Публичный API.** У каждого модуля один вход — barrel `index.ts` (или
   интерфейс-порт в `src/core/ports/`). Снаружи импортируем **только** его, не
   лезем во внутренности (`@/modules/economy` — да; `@/modules/economy/internal/...`
   — нет).
2. **Зависимости — однонаправленные** (как слои): нижние не знают о верхних.
   Граф ацикличен.
3. **Связь через порты, а не реализации.** Верхние модули зависят от интерфейса
   (`IPlayerService`, `ITradeService`…), конкретику подставляет `DIContainer`.
   Это уже работает (есть `MockPlayerService` и пр.) → модули тестируются с
   моками независимо.

## Карта модулей

| Модуль | Папка(и) | Зависит от | Ответственность |
|--------|----------|-----------|-----------------|
| **contracts** | `src/types`, `src/config` | — | Типы, enum'ы, баланс-константы. Лист графа. |
| **domain** | `src/domain` | contracts | Чистые сущности (Player, Galaxy, NpcShip…), без Pixi/ONNX/DOM. |
| **persistence** | `src/data`, `src/validation` | domain | Сейвы, миграции, Zod-схемы, IndexedDB. |
| **ai** | `src/ai`, `src/systems/npc/*Brain*` | domain | ONNX-registry, воркеры, brains, нарраторы, fallback. |
| **economy** | `src/systems/TradeSystem*`, `Market` | domain | Цены, торговля, легальность. (EPIC-001/006) |
| **living-galaxy** | `src/systems/npc`, `GalaxySimulator` | domain, ai | Спавн/симуляция NPC, off-screen события. (EPIC-003) |
| **quests** | `src/systems/quest*`, `quests/*` | domain, ai | Квест-менеджер, текст-квесты. (EPIC-005) |
| **combat** *(новый)* | `src/systems/combat` | domain, ai | Тактический бой. (EPIC-002) |
| **engine-core** | `src/systems/GameEngine`, `src/core` | все сервисы **через порты** | Оркестрация: сцены, игровой цикл, DI, сейв-координация. |
| **presentation** | `src/presentation` | engine-core (порты), domain (read-only) | Pixi-сцены, спрайты, ввод, рендер. |
| **audio** *(новый)* | `src/audio` | engine-core (хуки состояний) | `AudioManager`, кроссфейд по ключу состояния (см. AUDIO_TRACKLIST.md). |

> `requirements/` (docs) и `assets/` — не код-модули, развиваются независимо и так.

## Правило зависимостей (одной строкой)
```
contracts ← domain ← {persistence, economy, ai, living-galaxy, quests, combat}
          ← engine-core ← {presentation, audio}
```
Стрелка = «знает о». Никаких обратных и боковых импортов между сервис-модулями:
если economy нужны данные NPC — это идёт через порт/engine-core, а не прямым
импортом `living-galaxy`.

## Как делать независимо (рецепт на модуль)
1. Объяви/обнови **порт** в `src/core/ports/` (интерфейс сервиса).
2. Реализуй модуль за портом; наружу торчит только `index.ts`/порт.
3. Дай **mock** реализации (как `src/tests/mocks/MockPlayerService.ts`).
4. Покрой модуль unit-тестами против интерфейса (без других модулей).
5. Подключи в `DIContainer`. Интеграция — в одной точке.

→ Две команды могут пилить, например, `combat` и `economy` параллельно: каждая
против своего порта + моков, не дожидаясь друг друга.

## Enforcement (чтобы границы не размывались)
- ESLint-правило на запрещённые пути. Вариант на `eslint-plugin-boundaries`
  (элементы = модули, разрешённые рёбра = граф выше), либо проще —
  `import/no-restricted-paths` (zones): запретить `presentation → systems/*`
  мимо портов, `domain → ai/pixi` и т.п.
- Барель-импорты: настроить так, чтобы глубокие импорты (`.../internal/...`) были
  запрещены линтом.
- CI уже гоняет `npm run lint` — правило встанет в существующий гейт.

## Что НЕ делаем сейчас (осознанно)
- **Не** дробим на отдельные npm-пакеты/воркспейсы. Для одного Vite-приложения
  это лишняя цена. Если позже понадобится отдельная сборка/версионирование —
  модули уже изолированы портами, и вынос в `packages/*` (npm workspaces +
  `tsconfig` project references) станет механическим.
- **Не** переписываем существующий код — только проводим границы и включаем линт
  инкрементально (по модулю за раз).
