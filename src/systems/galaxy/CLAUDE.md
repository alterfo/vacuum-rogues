# Galaxy System Conventions

## Galaxy Balance

Completed `20260611-overmind-equilibrium-balance`:
- `Galaxy` tracks two hostile factions separately: `overmindSystems: string[]` (loss-condition) and `pirateSystems: string[]` (difficulty/narrative). `addPirateSystem` / `addOvermindSystem` are mutually exclusive (each removes from the other list). **Never call `removeOvermindSystem`/`removePirateSystem` directly from outside `Galaxy`** — use `galaxy.tryLiberate(systemId)` which handles both types and emits the `SYSTEM_LIBERATED` news event.
- **Loss gate**: always call `galaxy.isOvermindVictory(GAME_BALANCE.OVERMIND_LOSS_GRACE_DAYS, GAME_BALANCE.OVERMIND_LOSS_MIN_SYSTEMS, galaxy.gameDays)`, never the bare `isOvermindMajority()`. The grace period and min-systems guard prevent instant-loss on small/fresh saves.
- **Self-balancing tick**: `OvermindBalance.ts` exports `stepOwnershipTick` — a pure function (no side effects, no GameEngine coupling). `GalaxyStatusIndicator.ts` exports `computeGalaxyThreat` — thresholds: safe <20%, caution 20–35%, warning 35–45% (`GAME_BALANCE.OVERMIND_WARNING_THRESHOLD`), critical ≥45%. Both modules are pure; keep them that way.
- **Hostile-system combat difficulty**: `CombatScene` applies `OVERMIND_COMBAT_HP_MULT` / `OVERMIND_COMBAT_DAMAGE_MULT` when `isHostileSystem: true` is set in its `CombatContext`. Since the `20260616-realtime-inflight-combat` plan, regular NPC fights no longer transition to `SceneType.COMBAT` — they resolve in-flight via `CombatModule` (real-time auto-fire), which does **not** currently apply these multipliers. `CombatScene` (and the multipliers) now only run for the OVERMIND-core boss prompt and scripted text-quest encounters; any code that still transitions to `SceneType.COMBAT` from an overmind/pirate system must set `isHostileSystem: true`. **Known limitation / follow-up**: porting the hostile-system difficulty scaling into the in-flight `CombatModule` is unimplemented — overmind/pirate-system NPC fights are currently no harder than neutral ones.
- **`NewsEvent` type convention**: any new `NewsEvent.type` literal must also be added to `NEWS_TYPE_LABEL` and `NEWS_TYPE_COLOR` maps in `InfoCenterScene.ts`, and to the Zod enum in `schemas.ts`. Current types: `SYSTEM_LIBERATED`, `SYSTEM_CAPTURED`, `LIBERATION_CAMPAIGN`, `OVERMIND_EXPANSION`, `PIRATE_SURGE`, `NPC_QUEST_COMPLETE`, `PIRATE_ATTACK`, `MARKET_SHIFT` — see `src/types/index.ts` for the full union. `LIBERATION_CAMPAIGN` carries optional `targetSystemId` / `stagingSystemId` / `liberationDate` fields.
- **Hostile systems / garrisons / liberation** (`NpcSimulator`): a captured system holds a standing garrison (Overmind = `OVERMIND` faction + `PATROL` role; pirate = `PIRATE` role), spawned by `ensureGarrison` and held in place (excluded from the wandering streams). Garrison/capture-fleet ships are tracked in in-memory sets (`garrisonIds`, `captureFleetIds`) that reset on load and rebuild on the next tick — never persisted. Capture needs ≥ `CAPTURE_FLEET_MIN` HUNT ships arriving with no defenders left. Liberation fires after `LIBERATION_CLEAR_DAYS` of zero garrison presence via a `gameDays`-based `liberationCountdown` `Map` (save-safe: rebuilds on load). When a system is freed by **any** path (convoy, DEFENSE quest, `tryLiberate`, countdown), `resolveLiberationDetection` despawns any leftover frozen garrison ships. `NpcShip.hostile` (`markHostile()` / `isAggressive()`) is the single source of truth for aggression; attacking one neutral propagates hostility to same-faction in-system neighbours.

## Market Population

Completed `20260616-populate-planet-markets`:
- Every planet's market is seeded at generation by `marketSeeding.ts::seedMarket(economyType, planetId)` → `{ availableResources, supplyVector, demandVector }`, applied via `planet.market.populate(...)`. It is **pure and deterministic** — seeded from `planetId` via `SeededRNG("market:"+planetId)`, never `Math.random` — so saves/replays reproduce identical vectors. Determinism is load-bearing: a non-deterministic seed would desync price drift across save/load.
- Wired in `GalaxySimulator` at **two** sites: the main generation loop (≈L89) and the faction-home override in `assignFactionHomeSystems` (≈L632), which **re-seeds under the override economy** — the override wins for faction-home planets. Any new place that sets `planet.market.economyType` must also call `populate(seedMarket(...))`, or the market falls back to the empty stub (`new Market([], [], [])`) and the whole dynamic-pricing layer goes inert.
- **Loaded saves — known gap:** population runs only during fresh generation. Saves created *before* this feature carry empty stub markets, and the load path (`GameEngine.rehydrateLoadedState`) only restores prototypes — it does **not** re-seed. On those saves the dynamic-pricing layer stays inert. No schema migration is needed (no persisted *field* was added; the arrays already existed, just empty), but a load-time re-seed of empty markets is the follow-up — wire it into `rehydrateLoadedState` after the prototype loop (skip markets with `availableResources.length > 0`, seed via `seedMarket(market.economyType ?? system.economyType, planet.id)`).
- Every planet trades the **full** `ResourceType` catalogue; cross-planet spreads come from economy-biased supply/demand, not from which goods exist. Vectors are clamped `> 0` (pricing divides by supply).
- `seedMarket` derives bias from `economyBaseline()` *inverse* (cheap baseline ⇒ abundant supply, low demand) so the dynamic vectors agree in direction with the static `econMult` in `TradeSystem.getMarketPrice()`. `economyType` is written back on re-seed to keep static and dynamic in sync.
- `Market.priceMultipliers` is the **dynamic** layer only (trade impact + events); `advanceMarketDay` mean-reverts it toward **1.0, not the economy baseline** — the baseline is already applied separately as `econMult` in pricing, so reverting toward it too would double-apply the economy effect and widen every arbitrage route instead of closing it.
- **Persistence caveat:** `StarSystemSchema` (`schemas.ts`) has no `planets`/market sub-schema, so markets are **not** Zod-validated; they persist as raw JSON through `SaveStateSerializer`'s `JSON.stringify`/`JSON.parse`. Don't assume `GalaxySchema.parse` guards market structure — it strips `planets` entirely.
- **Two divergent price formulas (follow-up):** populating markets *activates* a pre-existing inconsistency. The player-facing trade screen prices via `TradeSystem.getMarketPrice` (per-resource `basePrices`, regressor, reputation, `econMult`, drift multiplier, clamped to `[base×0.3, base×3.0]`), but `Market.getPrice` — used by `GalacticRegistry.indexMarkets` (the info-center "[РЫНОК] best price" listings the player reads) **and** `NpcSimulator.pickTraderCargo` — uses raw `round(demand/supply × 100 × mult)` with **no** base price, econMult, or clamp. Before this plan, production markets were empty so these listings showed nothing; now they show numbers that don't match (and can rank a different "best" planet than) what the trade screen actually charges. Unifying them needs a player-independent reference price (the registry has no `Player`, which `getMarketPrice` requires), so it's a separate design task — land it with `20260616-living-trade-economy-rumors.md`, not here.

## DialogueSystem

**`startDialogue` deletes the previous session's timestamped key when re-indexing the NPC** — the map holds ≤ 2 entries per NPC (never grows unboundedly). Regression test: `src/tests/dialogueSystem.test.ts`.
