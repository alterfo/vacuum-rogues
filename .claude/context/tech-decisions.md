# Технические решения и ADR

## ADR-001: PixiJS 8 для рендеринга

**Статус**: Принято

**Контекст**: Нужен 2D рендеринг для браузерной игры с поддержкой WebGL и Canvas fallback.

**Решение**: PixiJS 8
- Зрелая библиотека с активным развитием
- WebGL2 с автоматическим fallback на Canvas
- Хорошая производительность для 2D
- Большое сообщество

**Альтернативы**:
- Phaser: Слишком тяжелый, много ненужных фич
- Three.js: Избыточен для 2D
- Raw Canvas: Слишком низкоуровнево

**Последствия**:
- Необходимо следить за lifecycle объектов
- Event handling через eventMode

## ADR-002: ONNX Runtime Web для AI

**Статус**: Принято

**Контекст**: Нужна генерация диалогов и AI-противники без серверных вызовов.

**Решение**: ONNX Runtime Web
- Запуск моделей локально в браузере
- Поддержка Web Workers (не блокирует UI)
- Кэширование в IndexedDB

**Модели**:
- T5-small: Генерация диалогов
- GRU: Эмоциональный трекинг
- VAE: Вариативность ответов
- PPO: Тактический AI

**Альтернативы**:
- LLM API (OpenAI, Claude): Требует сервер, задержки, стоимость
- TensorFlow.js: Хуже поддержка трансформеров

**Последствия**:
- Большой размер моделей (нужно кэширование)
- Ограничения по размеру моделей

## ADR-003: 4-слойная архитектура

**Статус**: Принято

**Контекст**: Нужна поддерживаемая архитектура для растущего проекта.

**Решение**: Layered Architecture
```
Presentation → Systems → Domain → Infrastructure
```

**Правила**:
- Зависимости только вниз
- Domain не знает о UI и базе данных
- Systems содержат бизнес-логику
- Presentation только рендеринг

**Последствия**:
- Легко тестировать domain изолированно
- Можно менять рендеринг без переписывания логики

## ADR-004: Zod для валидации сохранений

**Статус**: Принято

**Контекст**: Сохранения должны быть валидными и совместимыми между версиями.

**Решение**: Zod schemas
- TypeScript-first валидация
- Автоматическая генерация типов
- Детальные ошибки валидации

**Альтернативы**:
- JSON Schema: Нет интеграции с TypeScript
- io-ts: Более сложный синтаксис

**Последствия**:
- Схемы нужно обновлять при изменении моделей
- Миграции при изменении структуры сохранений

## ADR-005: Гексагональная система координат

**Статус**: Принято

**Контекст**: Навигация по карте галактики и тактический бой.

**Решение**: Axial coordinates (q, r)
- Простая математика для соседей
- Легко конвертировать в экранные координаты
- Используется в обоих контекстах

**Альтернативы**:
- Cube coordinates: Избыточны для 2D
- Offset coordinates: Сложная математика

**Последствия**:
- Единый HexGrid для карты и боя
- Pathfinding работает одинаково везде

## ADR-006: Playwright для E2E тестов

**Статус**: Принято

**Контекст**: Canvas-приложение сложно тестировать через DOM.

**Решение**: Playwright
- Поддержка скриншотов для visual regression
- Cross-browser тестирование
- Хорошая интеграция с CI

**Подход к тестированию Canvas**:
1. Unit тесты для логики (Vitest)
2. E2E тесты для пользовательских сценариев (Playwright)
3. Visual regression для UI (Playwright screenshots)

**Последствия**:
- Нельзя тестировать внутреннее состояние Canvas
- Тесты зависят от визуального вывода

## ADR-007: Dependency Injection через DIContainer

**Статус**: Принято

**Контекст**: Нужна возможность подменять сервисы для тестирования.

**Решение**: Простой DI Container (singleton)
- Регистрация сервисов при старте
- Resolve по интерфейсу
- Без автоматического wiring

**Альтернативы**:
- InversifyJS: Избыточен для наших нужд
- Manual DI: Слишком много бойлерплейта

**Последствия**:
- Легко мокать сервисы в тестах
- Сервисы создаются явно, не магически

## ADR-008: Game Loop через requestAnimationFrame

**Статус**: Принято

**Контекст**: Плавная анимация и обновление игры.

**Решение**: requestAnimationFrame + deltaTime
- Синхронизация с refresh rate монитора
- deltaTime для frame-independent логики
- Пауза автоматически при потере фокуса

**Последствия**:
- Все движения должны учитывать deltaTime
- Тяжелые операции могут вызвать пропуск кадров
