# Overmind Endgame Arc

The OVERMIND is an escalating, spreading endgame arc: it captures systems over time culminating in win (break the core), loss (galaxy consumed), or New Game+. Pacing targets a **2–3 in-game-year campaign** (1 year = 360 days, hard ceiling 1080 days) per `docs/plans/20260706-three-year-campaign.md` — see that plan for the full design record and the (still-open) win-rate gate.

## The spread machine

`advanceOvermind(state, galaxy, day, config)` (`src/systems/overmind/overmindSpread.ts`) is deterministic by `(galaxy.id, day, systemId)` (no RNG): past `graceDays` it captures `capturesPerTick` **frontier** systems every `spreadIntervalDays`, then re-derives `dormant → advancing ⇄ contained → won|lost` from the post-capture Overmind share. Returns `captured` ids for the caller — never mutates the galaxy. The fixed `OVERMIND_SPREAD_GRACE_DAYS`/`OVERMIND_SPREAD_INTERVAL_DAYS` levers were **removed** — spread cadence is now fully adaptive (below).

**Frontier selection is proximity-biased, not pure-hash.** Candidates are ranked primarily by BFS warp-hop distance (undirected graph, same rationale as `frontierSystems`) to the **most recently captured system** — derived as `galaxy.overmindSystems[length-1]` (`addOvermindSystem` appends in capture order; liberation splices in place), no new state. `hashStr` only tiebreaks within a distance band; unreachable candidates rank last via a `MAX_SAFE_INTEGER` sentinel (not `Infinity` — NaN comparator hazard). Still fully deterministic by `(galaxy.id, day, systemId)`. This is the residual fix for the front "appearing from all sides": one contiguous blob's border no longer jumps between its far edges.

## Adaptive difficulty (keyed to player power, not fixed day phases)

`playerPowerIndex` (`src/systems/campaign/playerPower.ts`) is a pure `clamp01` weighted blend of normalized hull/weapon/credits/rank (`POWER_INDEX_WEIGHTS`/`POWER_INDEX_*_MIN`/`_MAX` in `balance.ts`), read from the canonical `ShipLoadout`/`GearCatalog`. Two guards make "gentle while weak, relentless once armed" safe:

- **Ratchet**: `campaignPeakPower` never decreases (`ratchetPeakPower`), persisted as an **optional additive** field on `SaveState`/`GalaxySchema` (absent ⇒ derive from current loadout on load — no migration, no version bump). Updated every EOD tick, not just on save.
- **Baseline creep**: after `ADAPTIVE_CREEP_START_DAY` (360), the spread interval is floored at `ADAPTIVE_CREEP_MIN_DAYS` (12) regardless of power — a permanently idle run still resolves well before day 1080, so the loss gate stays measurable.

`adaptiveSpreadIntervalDays(day, dayZero, peakPower)` (`src/systems/campaign/adaptivePacing.ts`) = `lerp(ADAPTIVE_SPREAD_SLOW_DAYS=45, ADAPTIVE_SPREAD_FAST_DAYS=10, clamp01(peakPower))`, gated by `ADAPTIVE_GRACE_DAYS=90` (no spread before grace). `DayTickController.advanceOvermindArc` builds the spread config from these each tick via the **optional** `updateCampaignPeakPower` dep (absent ⇒ 0 ⇒ slowest cadence — legacy DI sites stay byte-identical).

Combat scaling revives the previously-dead `OVERMIND_COMBAT_HP_MULT`/`OVERMIND_COMBAT_DAMAGE_MULT` levers: `hostileScaling(power, mode)` (`src/systems/campaign/hostileScaling.ts`) lerps `HOSTILE_SCALING_WEAK_MULT=0.9` → `1.5` for **held-system** combat (garrisons), composed with `DIFFICULTY_HOSTILE_SCALING` for HARD. `neutralScaling(power, mode)` extends the same gentling to **neutral-system** wandering packs (`NEUTRAL_SCALING_WEAK_MULT=0.4` → `1.0`, incoming damage only — offense unscaled). `overmindGarrisonPowerBonus` shifts the spawned garrison range up by up to `OVERMIND_GARRISON_POWER_MAX_BONUS=2`. `NEUTRAL_AGGRO_POWER_THRESHOLD` (= the battle-ready threshold) gates whether wandering neutral packs chase a ship at all — a weak ship isn't hunted; garrisons and already-engaged combatants are never shielded. All wired via **optional** DI deps (absent ⇒ neutral/legacy behavior, byte-identical).

Escalation is *felt*, not silent: `activeEscalationStages` (`src/systems/campaign/escalationNotices.ts`) derives `NOTICED`/`HARDENING`/`FINAL_PUSH` bands from ratcheted power + Overmind share and fires a one-shot `CAMPAIGN_ESCALATION` news event per stage (fire-once tracker keyed by galaxy id; a loaded mid-game save seeds silently, never spams retroactive news).

**Combat is round-based with a disengage window** (`src/systems/combat/combatRounds.ts`): a round removes at most `GAME_BALANCE.combatRoundHullFraction` (0.34) of MAX hull, so hull can never drop full→zero in a single resolution step — both the live player and the headless agent get a reaction window (flee/fight) between rounds. Gated on `getCampaignPeakPower !== undefined && mode !== GOD` (GOD's hull floor already prevents the one-shot; legacy DI stays byte-identical flat combat).

## The garrison layer: growth, bud-off, liberation assaults (NpcGarrisonCombat)

An **additive concrete-ship layer** in `src/systems/npc/NpcGarrisonCombat.ts` (composed by `NpcSimulator`; plan: `docs/plans/20260709-overmind-garrison-growth.md`) that makes expansion feel organic — a captured system's garrison grows, buds off a traveling capture fleet, and rangers mass to retake fresh captures with real combat. It does **not** touch `advanceOvermind()`'s abstract pacing arc, and the pre-existing fixed-interval `assembleCaptureFleet` (60-day) / `assembleLiberationCampaign` (50-day) triggers still run unchanged alongside it.

- **Garrison growth**: `fillGarrison` records each garrison's baseline count in `garrisonBaseline: Map<string, number>` — **clamped to the scaled garrison max** (after a load a fresh simulator re-records the then-present, possibly grown, count; raw re-anchoring would ratchet the band ~1.5× per reload), and a baseline **below the current scaled min is re-anchored up to it** (`anchorGarrisonBaseline` — a stale weak-era baseline puts the bud cap inside the replenishment band, turning the free daily top-up into a perpetual subsidized capture-fleet factory instead of organic growth). `growGarrisons` (called from `tick()` after `ensureGarrison`, every `GARRISON_GROWTH_INTERVAL_DAYS = 10`, isolated day-seeded RNG stream) adds +1 ship until `round(baseline × GARRISON_GROWTH_BUD_THRESHOLD = 1.5)`, counting **garrison members only** (`countGarrisonMembers` — wandering Overmind/pirate visitors must not fake a threshold crossing or resurrect a cleared garrison). Gated adaptively: no growth while `overmindGarrisonPowerBonus(campaignPeakPower) < 1` (weak-era garrisons stay beatable — the seeded pacing gate in `sessionCompetence.test.ts` depends on this). Growth skips cleared garrisons (never resurrects a wiped one), systems under active Ranger assault (**siege freeze** — daily top-up would out-replenish attrition and make sieges unwinnable; `fillGarrison` skips them too), and the **player's current system** (a ship popping into existence — or a bud-off despawning defenders the player is tracking — reads as a glitch; same rule as the abstract resolvers).
- **Bud-off**: at the 1.5× threshold, `round(baseline × 0.5)` ships (clamped to available donors, min 1) peel off via the shared `launchCaptureFleet` helper as a `capture_bud_`-prefixed fleet in `captureFleetIds` — donor garrison ships are despawned and replaced one-for-one by fresh fleet ships, because `reconcileTransientState` rebuilds hold-sets from id prefixes on load (a repurposed `garrison_` id would be reclassified back into a garrison mid-flight). Target: a neutral warp-neighbor preferred (**undirected** scan via `undirectedNeighbors` — same one-way-edge rationale as `frontierSystems`), else a nearer-weighted neutral anywhere via `travelDays`. The fleet **travels** (multi-day) and is resolved by the existing `resolveCaptureFleets` real per-ship attrition siege — no new resolution logic. Baseline resets to the post-bud count so growth restarts; a skipped bud-off (no neutral target) leaves it untouched for retry.
- **Liberation targets fresh captures**: `recentlyCaptured: string[]` (FIFO, cap 5) is pushed at `resolveCaptureFleets`' single `SYSTEM_CAPTURED` emit site (covers periodic + bud-off fleets; captures by the abstract spread machine in `DayTickController` are **not** queued — plan-scoped). `assembleLiberationCampaign` drains it before the random-front scan (staging found via the **undirected** neighbor scan): re-capture moves an entry to the back; stale entries (liberated / already campaigned) drop; a landlocked entry (no friendly neighbor) stays queued for retry. The queue path consumes no RNG, so the random-front stream is byte-identical when it's empty.
- **Liberation assaults fight for real**: rally rangers arriving at a hostile system no longer roll the flat `CONVOY_LIBERATION_CHANCE = 0.2` (that flip **remains** for the unrelated `isConvoyPatrol` branch) — they join `liberationAssaultIds` (rebuilt on load from the `liberation_` convoyId prefix) and `resolveLiberationAssaults` runs the same per-ship attrition trade as `resolveCaptureFleets` against the garrison each tick. Garrison cleared ⇒ `galaxy.tryLiberate` (which emits the news itself); assault wiped ⇒ system stays hostile. The resolver **skips the player's current system** (same rule as the other abstract resolvers — the fight there is visible, and an NPC-credited flip under the player's nose would also rob `playerLiberations`) — but the already-freed **stand-down release runs before that skip** (releasing parked rangers is cleanup, not visible combat; deferring it would freeze the force for as long as the player camps the system they just liberated); a stale `liberation_` marker on a ranger parked in a non-hostile system is cleared by `reconcileTransientState` on load. Supporting rules that make sieges winnable: besiegers are excluded from `resolveGarrisonOffscreenCombat`'s no-retaliation prey scan and abstract off-screen combat (their fight is owned by the mutual-attrition resolver), and `dispatchLiberationRally` musters **galaxy-wide** (staged first, then nearest; `LIBERATION_RALLY_MAX_SHIPS = 8`) with hulls refitted to full at departure.

All new state (`garrisonBaseline`, `recentlyCaptured`, `liberationAssaultIds`) is transient `NpcGarrisonCombat`-private runtime state — never persisted, rebuilt via `reconcileTransientState`, no schema/migration impact. Constants live as module-level `const`s in `NpcGarrisonCombat.ts` next to `GARRISON_MIN`. Tests: `garrisonGrowth.test.ts`, `garrisonBudOff.test.ts`, `liberationRecentCapture.test.ts`, `liberationAssault.test.ts`, plus the proximity cases in `overmindSpread.test.ts`.

## Overmind ship identity: role, size tiers, loot, rename

Plan: `docs/plans/20260709-overmind-ship-identity-and-balance.md`. Overmind ships no longer borrow the PATROL role — they have their own identity across role, stats, art, name, and loot:

- **`NpcRole.OVERMIND`** (`src/types/index.ts`) — a 5th enum member with entries in every exhaustive map (`ROLE_STATS`/`ROLE_LOADOUT`/`ROLE_NAME`/`npcRoleTechLevel` in `npcRoleCatalog.ts`, re-exported from `NpcSimulator.ts`; `ROLE_SHIP_PREFIX`/`INTENT_COLORS` in `NpcShipSprite.ts`; `NPC_WEAPON_RANGE` in `npcWeapon.ts`; switch branches in `npcBehavior.ts`/`NpcBrain.ts`/`factionHostility.ts`). Persisted additively on `NpcShipSchema.role` — no migration. Base stats: hull 160 / shields 80 / shieldPower 5 (tougher than PATROL's 140/70/4); **damage stays 28 — the seeded letsplay campaign gate (`sessionCompetence.test.ts`) reds on ANY garrison damage increase** (empirically bisected; power climb stalls below battle-ready). Don't raise it without re-measuring that gate.
- **`sizeTier`** — optional `NpcSizeTier` (`"small" | "medium" | "large" | "boss"`) on `NpcShip`/`NpcShipInit`/schema (additive, no migration; absent on old saves ⇒ treated as medium/baseline). Garrison and capture-fleet spawns roll small/medium/large at 50/35/15 via `overmindSizeTierForId(id)` — a **deterministic id hash, not an rng draw**, so shared seeded rng streams stay byte-identical. Hull scales per tier (`OVERMIND_SIZE_TIERS` in `balance.ts`: small 0.8×, medium 1×, large 1.3×); damage is tier-flat below boss for the same campaign-gate reason. The boss is always `"boss"` with fixed stats centralized as `OVERMIND_BOSS_TIER` (450 hull / 45 damage) in `balance.ts` — the old ad-hoc 450/45 magic numbers are gone, but `OvermindBossController.spawnOvermindCoreCombatant` still re-applies hull/damage/sizeTier explicitly after the factory call, as a defensive re-apply for deps factories (e.g. test mocks) that ignore the `"boss"` tier hint — don't delete it as "redundant."
- **Art**: `shipArtPrefix()` (exported pure helper, `NpcShipSprite.ts`) resolves `Faction.OVERMIND` ships to prefix `` `overmind_${sizeTier ?? "medium"}` `` through the same `pickVariant("ships", prefix, npc.id)`; missing variants degrade via `pickVariant`'s existing fallback. Per-tier prompt entries live in `tools/comfyui/asset_prompts.json` (`ships` → `axes.role`, magenta-pink bioluminescent motif); **generating the `overmind_*` art is a manual ComfyUI step** — until run, the fallback art renders.
- **Rename**: ships are named `Жнец ${id}` (was `Доминатор`); capture news reads «…захвачена Жнецами!». Pinned by `overmindRole.test.ts`.
- **Size-scaled artifact drops**: `LootDropHandler.spawn()` scales by `OVERMIND_ARTIFACT_DROP` (`balance.ts`, keyed by `NpcSizeTier`): `artifactChanceMult` small 1× / medium 1.4× / large 2× / boss 4×-capped-at-1.0, plus `bonusLootRolls` (large +1, boss +2 guaranteed items atop the flat 0–2 roll). Rng consumption order is unchanged; tier-less and non-Overmind ships keep today's flat `ARTIFACT_DROP_CHANCE` exactly.
- **Faction label** is unified on `FACTION_LABEL[Faction.OVERMIND] = "Сверхразум"` — scenes read the shared `factionDisplayLabel()` helper (`factionConfig.ts`), and the `faction.OVERMIND` i18n values were repointed (ru «Сверхразум», en "Overmind"); the old «Предтечи»/"Precursors" contact-panel divergence is gone (the ru lore line naming the ancient race keeps «Предтечи» deliberately).

**Engine speed retune + apex gating** (same plan): the derived engine speed formula is now `spd = (0.066 + techLevel * 0.022) * m` (`ShipLoadout.ts`) — starter `eq_engine_i` holds 0.11, apex `eq_engine_v` lands at 0.22 (exactly 2× starter, was 2.36×). The apex now clears the in-flight interceptor pursuit speed (`npcCruiseSpeed` 0.2) by only ~10% — flagged as a balance follow-up in `GearCatalog.ts`/`balance.ts` comments. `eq_engine_v` additionally carries an opt-in `minDay` catalog field (`APEX_ENGINE_MIN_DAY = 1050`, `balance.ts`) consumed by `ShopGenerator` as a stocking floor — it can't appear in any shop before ~year 3 regardless of tech level; no other item sets `minDay`. `minDay` is also enforced on the **combat-loot** path, not just shops: `NpcRole.OVERMIND`'s loadout carries the same "Двигатель ур.3" (→ `eq_engine_v`) token as its scan summary, so `LootDropHandler.spawn(npc, x, y, rng, day)` and its private `pickModuleId` filter any loadout token whose resolved gear has an unmet `minDay` out of the drop pool before that day — otherwise killing any Overmind garrison ship (encountered from day 1) would bypass the shop-only gate entirely. `NpcShipManager.spawnLootForNpc` threads the live `galaxy.gameDays` in; the `day` param defaults to `Infinity` (no gate) only for direct/test callers that don't track the calendar.

## The overmind campaign quest chain

`src/systems/quests/campaignChain.ts` — a 6-step chain (distress → recon → requisition → liberation → counteroffensive → core) gated by a pure predicate over `(questLog.completedQuests, overmindShare, peakPower, arcStatus)`: strictly in order, milestone-banded (not day-banded), no new persisted state (completion reuses `QuestLog`). Offered via `GameEngine.getQuestBoard`.

## Critical invariants — do NOT revert these

- **`frontierSystems` treats the warp graph as UNDIRECTED.** ~25% of galaxy warp links are one-way (`ensureConnectivity` bridges), so a directed-only scan misses systems reachable via one-way outgoing edges — stalls the front for days.
- **Win requires GENUINE ENGAGEMENT**: `coreBroken`/`eradicated` are gated on `engaged = state.lastSpreadDay >= 0` (arc actually spread past grace). `peakThreat` is a *false* proxy: it captures the initial Overmind share (e.g. 2/30 ≈ 0.067) during the grace window — without the gate, early clearance of starting systems fired spurious ПОБЕДА. The in-flight **core-kill** win is a separate path (`handleInFlightDeath` → `showGameOutcomeScreen(true)`) and is unaffected.
- **Win also requires PLAYER participation**, not just NPC equilibrium churn: `coreBroken`/`eradicated` additionally require `(state.playerLiberations ?? 0) > 0` (optional additive field, `Galaxy.tryLiberate(id, "player")` at genuine player-driven liberation call sites). Found live: the NPC equilibrium clearing the *last* Overmind systems on its own fired a spurious win at day ~140 with a never-battle-ready player — fixed by requiring the player to have actually liberated (or core-killed) at least once.
- **The arc OWNS the front; equilibrium only churns pirates.** `DayTickController` (invoked from `GameEngine.advanceGalaxyDay()`) passes `stepOwnershipTick` a `freezeOvermind: true` when Overmind holds territory, so the equilibrium's ~25% ceiling can't cap the arc below its loss line or liberate the core spuriously.
- **The two starting OVERMIND systems must land as one warp-connected cluster.** `GalaxySimulator.generateGalaxy` picks the core (most distant from centre) and forces the second starter to be a warp-connected neighbour of it (excluding the player's home system) — an independently-chosen distant second seed grows as two disconnected blobs from day one (`frontierSystems` merges every Overmind system into one hash-ranked pool regardless of cluster), reading as the front "appearing from all sides" instead of one advancing line.

Regressions: `overmindNoSpuriousVictory.test.ts`, `overmindSpread.test.ts`, `playtest/overmindArc.test.ts`, `galaxy/overmindSpawnCoherence.test.ts`, `campaign/adaptivePacing.test.ts`, `campaign/hostileScaling.test.ts`, `campaign/escalationNotices.test.ts`, `campaign/campaignChain.test.ts`, `combat/combatRounds.test.ts`, `tryLiberateSource.test.ts`.

## Persistence

`Galaxy.overmindArc: OvermindSpreadState` persists via `GalaxySchema` (migration defaults old saves to `initialOvermindSpreadState()`). `playerLiberations` is an optional additive field on that same state (absent ⇒ 0, no migration). `campaignPeakPower` is a separate optional additive field on `SaveState` (absent ⇒ derived from loadout on load, no migration).

## Win/loss/NG+

Won/lost drives `showGameOutcomeScreen` (overlay over current scene, gated on `_outcomeShown` — not a terminal-scene transition). New-Game+ (`newGamePlus.ts`): capped credit slice + carried rank/faction + one-notch-harder difficulty (`nextCycleGameMode`: GOD→NORMAL→HARD→HARD). Tune carry in `balance.ts` (`NEW_GAME_PLUS_*`).

## ⚠️ Known-unmet gate: 99% win-rate (as of 2026-07-07, updated 2026-07-13)

The plan's 99%-win-rate acceptance gate (`≥ 297/300 sessions win, ≤ 1080 days, 0 deaths`) is **NOT met**: the 300-session measure (Task 19) landed at **2.0% win-rate** (6 win / 18 loss / 270 died / 6 timeout), death-dominated (90% of runs). Five rounds of escalation (neutral-system gentling, mid-combat reaction, neutral-aggro gating, near-edge flee-jump, round-based combat with a disengage window) each landed real, tested, live-player-beneficial improvements but the win-rate plateaued at ~16–24% throughout — the root bottleneck is the **arming-up path** (battle-ready reached in only ~14–16% of runs), not per-fight survivability. Full record: `docs/plans/20260706-three-year-campaign.md` Task 9/11/19 notes. This is a known, measured, open gap — not a regression to silently "fix" by loosening the gate.

**2026-07-13 follow-up (`docs/plans/20260713-campaign-win-rate-architecture.md`): downward garrison-count discount, still plateaued.** Added `overmindGarrisonPowerDiscount()` (mirrors the existing upward `overmindGarrisonPowerBonus()`, monotone non-increasing, `OVERMIND_GARRISON_POWER_MAX_DISCOUNT=1`) so a low-power player faces a smaller Overmind-held-system garrison (`[4,9]` vs the fixed `[5,10]` floor at power 0) — targeting Task 9's own diagnosis that a battle-ready 180/49 ship still can't solo the fixed `GARRISON_MIN=5` standing garrison. Measured at 50 sessions: **4.0% win-rate** (2 win / 2 loss / 43 died / 3 timeout), median win day 231 — still inside the prior 2–24% plateau band, below the plan's own ≥50% interim gate. Both named fallback levers were ruled out: `HOSTILE_SCALING_WEAK_MULT` and `OVERMIND_GARRISON_POWER_MAX_BONUS` are both pinned by existing tests (exact-value / greater-than-zero assertions) and out of scope under the "never weaken a pinned test" rule. A diagnostic sweep of the unpinned `NEUTRAL_SCALING_WEAK_MULT` (0.4→0.15) produced byte-identical session outcomes to baseline, showing the dominant early-death mode (peak power 0.02–0.15, days 63–136, ~86% of sessions die before battle-ready) is gated by neither lever this mechanism controls. Most likely remaining cause: **pirate-held-system garrisons**, which are explicitly and permanently unscaled by design (`garrisonPowerScaling.test.ts:110-114` pins `pirateGarrisonCount` identical at power 0 vs 1) — out of this plan's scope by Task 1's own decision. Recommendation for a future plan: a separate, pirate-specific garrison discount, which would need its own pinned-test change and its own explicit scope decision.

**Code review addendum (2026-07-13):** a closer read of `overmindGarrisonPowerDiscount(p) = Math.floor((1 - clamp01(p)) * maxDiscount)` at the shipped `maxDiscount=1` shows it is a knife-edge step, not a graded ramp: for *any* `p` strictly above `0` (`floor((1-p)*1)`) the result is `0` — the discount is nonzero only at the exact literal `powerIndex === 0`. Since `campaignPeakPower` is a ratchet seeded from `powerIndexFromLoadout` (calibrated to read ≈0 only at the very start of a fresh run) and never decreases, it goes strictly positive after the player's first credit/rank/gear change and stays there — i.e. the discount is realistically active for at most the first few in-game ticks of a run, not through the 0.02–0.15 power band where the plan's own death census places most early deaths. This is a more concrete candidate explanation for the measured no-op result than the pirate-garrison theory above (though both may contribute) — a future attempt at this lever should raise `maxDiscount` to ≥2 (so `floor()` produces a real intermediate band over the 0.02–0.15 range) and separately address the Task-2 GOD-mode regression (e.g. exempting GOD mode, which already floors hull and has no survivability upside to gain) instead of shrinking `maxDiscount` to fit around it.

**2026-07-19 addendum (gear-catalog & garrison-power-ceiling plan, Task 4): `maxDiscount` was since raised to 4 (per `docs/plans/20260713-campaign-winrate-100pct.md`'s own Task 2, addressing the knife-edge above exactly as recommended) — `overmindGarrisonPowerDiscount` now grades smoothly (4→3→2→1→0) across the realistic power band (~0.02–0.33). This plan opened assuming the discount was still the old knife-edge (a stale code comment, since fixed) and proposed rescaling it again; that premise was wrong and the fix was not made — the discount is already reasonably tuned for the power range real sessions reach. A fresh 50-session measurement with a new metric (`firstPlayerLiberationDay`/`playerLiberationRate`, distinct from the pre-existing `firstLiberationDay` proxy which fires on ANY liberation, player or NPC) found: solo-liberation happens in 24% of sessions (avg day 340) — mostly as gradual, incidental attrition of the already-small discounted garrison through ordinary combat (median 2 simultaneous combatants per fight), not via the deliberate `MemoryHeuristicPolicy` "Overmind-slayer" assault tier (gated on `isBattleReady()`, which only 10% of sessions ever reach). Of the sampled battle-ready sessions, most **died shortly after** rather than liberating — the slayer tier's stand-and-fight behavior appears to correlate with dying, not winning. So the garrison bonus/discount formula is not the active constraint; the real blockers are (a) the battle-ready rate itself (the arm-up/affordability wall — see the 2026-07-13 addendum above and `docs/plans/20260719-autopilot-combat-coverage-and-campaign-pacing.md`'s Task 2b) and (b) a newly-observed risk in the slayer tier's engage decision, tracked as that plan's open **Task 4b** (not yet investigated). Do not re-attempt a garrison-formula-only fix without addressing (a) or (b) first — this addendum's data suggests it would repeat the "still plateaued" result.
